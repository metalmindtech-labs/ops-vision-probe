## Check 1 — Migration review (DONE, see below)
Reviewed in `supabase/migrations/20260826000000_course_jobs.sql`:
- New standalone table `public.course_jobs`; no FKs in/out → drop is a clean reverse.
- `idempotency_key` is `NOT NULL UNIQUE` (DB-level dedupe) + app-level check + a
  `23505` race-catch in `lib/radar/supabase-store.ts` → idempotency is airtight.
- `status` CHECK restricts to accepted|queued|generating|reviewing|ready|failed.
- Indexes on `signal_id`, `status`; unique key indexes `idempotency_key`.
- RLS enabled, **no** anon/auth policies → service-role only.
- Down migration provided: `20260826000000_course_jobs_rollback.sql`.

### Option B — a real Radar staging dispatch
Point Radar **staging only** at the staging receiver, dispatch one converted
signal, then confirm each acceptance criterion:

| Criterion | How to confirm |
|---|---|
| Radar receives **202 Accepted** | Radar job row → `accepted`; receiver returns `{status:"accepted",job_id,status_url}` |
| Duplicate dispatch **deduplicated** | Re-send same brief → receiver returns **200** `{deduplicated:true}` with the **same** `job_id`; `select count(*) from course_jobs where idempotency_key=$1` = **1** |
| Job status **progresses** | `GET /api/course-generation-jobs/<job_id>` returns the stored status; as the (future) pipeline advances, values move accepted→…→ready |
| **No course content generated by Radar** | Inspect `course_jobs.brief` jsonb → contains only signal/demand/audience/hypothesis; **zero** modules/lessons/quizzes/syllabus. Receiver rejects any such field with `400 forbidden_content` |
| **LearnForge is the only generator** | The 202 path only records a job; the `TODO(generation)` seam in `route.ts` is where LearnForge (not Radar) will generate later. Radar has no generation code path |

DB spot-checks:
```sql
select id, status, signal_id, idempotency_key, created_at from public.course_jobs order by created_at desc limit 5;
-- confirm brief has NO content fields:
select jsonb_object_keys(brief) from public.course_jobs limit 1;  -- expect: schema_version, signal_id, source, demand_evidence, audience, commercial_hypothesis, generation_constraints, callback, idempotency_key
```

## Production (ONLY after staging passes + approval)
Low-traffic window, with these prepared **before** applying:
```bash
# 1) Backup (table is new; this captures state for a clean point-in-time)
pg_dump "$PROD_DB_URL" --schema-only --table=public.course_jobs > backup_course_jobs_schema.sql
pg_dump "$PROD_DB_URL" --data-only  --table=public.course_jobs > backup_course_jobs_data.sql  # empty on first apply
# 2) Apply
supabase db push   # against linked PROD project
# 3) Rollback command (ready to paste if needed)
psql "$PROD_DB_URL" -f supabase/migrations/20260826000000_course_jobs_rollback.sql
```
Because `course_jobs` is a brand-new, FK-isolated table, the rollback is a
non-destructive drop of only that table — `courses`, `user_purchases`, auth,
and Stripe data are untouched.

## Boundary reminders
- Radar discovers demand and dispatches a signed `CourseBriefV2`. It never
  generates syllabi/modules/lessons.
- LearnForge owns all generation, wired at the `TODO(generation)` seam AFTER a
  202. This runbook stops at "accepted" — it does not generate a course.
